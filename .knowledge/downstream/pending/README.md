# pending/ 目录说明

## 用途

存放来自下游项目的回流材料。目录名表示收件位置；历史材料可能已经提交或合并，实际进度须核对关联 PR、验收记录和回流登记，不能只按路径判断。

## 目录结构

```
pending/
└── {project-hash}/
    └── {contributor-name}/
        └── {commit-id}/
            ├── SUBMISSION.md     # 来源、问题、方案、边界及关联 PR
            ├── content/          # 候选材料或指向实际改动的说明
            └── tests/            # 验证材料；没有验证时明确标注
```

使用本目录的 [TEMPLATE.md](TEMPLATE.md) 填写提交；更完整的步骤见 [下游规范](../../../docs/downstream-spec.md)。已有历史提交中使用不同文件名时先核对内容，不直接移动或改写其审核结论。

## 使用流程

1. 下游在实际项目中确认问题，选择可公开的材料，按来源和提交 ID 建目录。
2. 填写 `SUBMISSION.md`，写明实际修改位置、验证情况、未解决项；不为凑目录重复复制实现。
3. 创建回流分支并提交 PR。`pending/` 默认被 Git 忽略，使用 `git add -f <本次提交目录>` 只加入这次选择的材料。
4. 维护者复现、去重和审核；将决定、关联 PR、发布位置及版本同步到 [backflow.yaml](../backflow.yaml)。候选被接受、代码已合并、包已发布分别记录。

这里没有统一可执行的 `/backflow review` 或 `/backflow accept` 命令。仓库的 [scripts/backflow.sh](../../../scripts/backflow.sh) 处理 CG → knowledge-graph 的上游上报，不能当作下游审核工具。工作台的反馈编号目前也不会自动生成 PR 或发布。

## 审核标准

- 是否解决实际问题，原始现象能否复现。
- 是否可复用，具体项目的业务判断是否留在项目侧。
- 来源、格式、适用范围和限制是否明确。
- 是否有验证证据，未验证部分是否如实标注。
- 材料是否适合公开，不包含账号凭证或私有业务数据。

维护和后续接通工作台的计划见 [维护与丰富方案](../../../docs/maintenance-and-growth.md)。
