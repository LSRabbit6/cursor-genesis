# 多门店零售 · 四个模式总览（v0.1.0）

> 这一页回答两件事：这次该挑哪个模式；挑了之后怎么并进设计稿。
> 四个模式都写成六段（目标 / 口径 / 数据源 / 分步 / 验收 / 不变量），和 delivery-data-app 的 `plan-templates/design-doc-six-sections.md` 一一对上。

## 一、挑哪个

| 你这次要做的事 | 挑 | 文件 |
|:--|:--|:--|
| 员工在群里或私聊里发文字、图片报一件事（报销、进货单、维修、补货），系统要接住、看懂、追问缺项 | 图文办理 | [image-text-intake.md](image-text-intake.md) |
| 店长、老板、会计、出纳要处理很多笔，分不清哪笔办了哪笔没办 | 角色待办 | [role-todo.md](role-todo.md) |
| 员工随口起的名字（费用名、商品名、收款方）五花八门，要事后整理成正式分类，下次能认出来 | 事后名称整理 | [post-hoc-naming.md](post-hoc-naming.md) |
| 老板随口说了一条规则，要落进系统 | 口径收件箱 | [caliber-inbox.md](caliber-inbox.md) |

一件事常常要挑两三个。例：「图文办理 + 角色待办 + 事后名称整理」是一条完整的报账链；口径收件箱是另外三个的口径来源，做任何一个都建议带上。

## 二、怎么并进设计稿

1. 每个模式文件的第 1 到第 6 段，对应你设计稿的第 1 到第 6 段。挑了几个模式，就把它们同一段的内容合在一起写。
2. 模式里的「例」「常见候选」只是帮你想全，不是答案。写进设计稿前，换成你仓里的真实对象和你使用者的原话。
3. 模式里每个〔待裁〕都原样进设计稿第 2 段「口径」。一条〔待裁〕在设计稿里写成这样：

   ```markdown
   - 〔待裁〕资料齐了以后，是直接转给店长，还是让员工再确认一次。——谁定：老板；原话：（还没问过）
   ```

   有原话就填原话、说话人、日期。没有就保持「还没问过」。**不攒问题清单去问他**，先出能看的预览，等他看着预览说。
4. 第 5 段「验收」里的场景，至少挑三条写进你的设计稿，并写清在哪看到结果（哪个页面、哪条记录、哪个命令）。

## 三、四个模式共用的分工

四个模式都按这张表分工。设计稿里每加一个环节，先问它属于哪一列。

| 谁 | 管什么 | 不许做什么 |
|:--|:--|:--|
| 程序 | 身份与权限、编号、去重、存储、队列、版本、状态转换、通知、统计笔数和金额 | 不替人做业务判断；不靠模型算合计 |
| AI | 看懂文字和图片、判断多笔的边界、从真实候选里比较、给建议和理由 | 不决定批准；不发明口径；不把建议写成已确认 |
| 人 | 发材料、补充和更正、按岗位做决定、确认名称整理、给口径 | — |

还有四条共用的底线，每个模式的「不变量」段都默认带上：

- **原件和原话先存，再理解。** 识别结果、模型意见都是派生记录，原件不能因为识别失败就丢。
- **未取到、空、零是三种状态。** 金额未知不写 0，收款方未知写「待确认」，不拿申请人顶上。
- **身份从服务端来。** 卡片上、网页上显示的名字和角色不是权限依据。
- **设计了、代码实现了、接入了、上线了、现场验收了，是五件事。** 交付时分开报，不用一个完成率盖住缺口。

## 四、这几个模式不管什么

- 不管怎么付款：出纳只记录真实付款，不发起转账。
- 不管库存、成本、盘点：费用流水推不出真实库存。
- 不管经营分析的判据：什么算异常、阈值多少，是每家老板自己的，走口径收件箱。
