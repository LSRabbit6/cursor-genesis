# 模式 · 角色待办（v0.1.0）

> 店长、老板、会计、出纳各自在私聊里收一份**本人权限内**的待办清单：一行一笔，点了马上看到结果，办过的不再提醒，没办的一直留着。
> 解决的现象：审批人点了通过以后，分不清哪笔过了；消息一多，不知道哪笔点过、哪笔没点；每家店各提醒一遍，跨店的人要在好几个群里找。
> 适用：一笔事要经过多个岗位依次处理，每个岗位每天有多笔。不适用：只有一个岗位、一天一两笔的场景（单笔卡片就够）。

## 1. 目标（并进设计稿第 1 段）

- 每个岗位在私聊里有一份清单，只列本人现在能处理的事；跨店的岗位一份清单汇总所有店，账仍按原门店归属。
- 一行一笔，看得出状态和能做的动作；要看原件和完整经过，再点开详情。
- 定时汇总不漏历史未办，也不因为刚处理了一条就重新推一整份。

## 2. 口径（并进设计稿第 2 段，全部〔待裁〕）

| 〔待裁〕 | 常见候选（只是帮你想全） |
|:--|:--|
| 每个岗位的清单里显示哪几列 | 发起人、门店、金额、费用类型、报账时间、收款对象、AI 建议、状态、操作 |
| 每个岗位能看到哪些店、哪个阶段 | 店长：本店待审核；老板：授权范围内待审批；出纳：已批准待付款、付款待核对 |
| 定时汇总几点发，每个岗位是否各自一个时间 | 只给一个岗位先开，其余先关、手动查 |
| 要不要加急即时提醒，什么算加急 | 先不做，留配置入口 |
| 每个岗位的动作叫什么、意味着什么 | 见第 4 段第 3 步的表；名字可以换，含义不能混 |

时间点没定的岗位，日程功能做好但先关着，手动打开清单照样能用；不许开发时悄悄替人定一个时间。

## 3. 数据源与对象（并进设计稿第 3 段）

先复用仓里已有的决定记录、私聊会话、可靠投递（发件箱）、单笔详情卡。清单**不另存一份审批结论**，审批正本仍是原来的决定记录。需要新增时：

| 对象 | 最少记什么 | 为什么 |
|:--|:--|:--|
| 提醒策略 | 人、岗位、范围、时区、时刻、是否启用、版本、依据（原话或「工程默认」） | 一个跨店老板是一条策略，不是每店一条 |
| 汇总批次 | 人、岗位、日期、截止时刻、状态（计划 / 空 / 已入队 / 已发 / 失败 / 不明）、快照及哈希 | 同一天同一岗位只发一次；重启不重发 |
| 进入阶段记录 | 单据、版本、岗位、进入时间、来源事件或决定 | 「今天该谁办」看进入本阶段的时间，不看最初报账时间 |
| 清单视图绑定 | 每行绑定 单据编号 + 版本 + 阶段 + 预览哈希 | 按钮指向对象，不指向「第几行」；翻页、筛选后旧按钮不会点错 |

## 4. 分步（并进设计稿第 4 段）

先做逐笔，批量放后面。

1. **清单查询。** 从服务端按当前身份和有效授权查本人待办，带分页、筛选（门店、状态、时间）、快照时间。不能「只取前几条」却不给翻页。某家店读取失败，清单里写「这家店暂未取得」，不能拿一份缺店的清单说全办完了。
2. **一行一笔。** 手机上一笔两三行：一行文字摘要（用图文办理模式里那份唯一事实摘要）、一行状态和 AI 建议、一行按钮。不把宽表硬塞进手机。金额、大类、状态、按钮不许被截掉。
3. **按钮语义按岗位。** 清单长得一样，动作含义不一样：

   | 岗位 | 主要动作 | 结果 |
   |:--|:--|:--|
   | 店长 | 通过、驳回、详情 | 推到老板或退回；不替老板决定 |
   | 老板 | 通过、驳回、讨论、详情 | 形成本人决定；通过进入付款待办，**不等于已付** |
   | 会计 / 出纳 | 办理付款、反馈问题、详情 | 只记录真实付款；点一下不算转账 |

   按钮来自服务端给的「当前允许的动作」，不按列表里的状态名自己推。一人兼几个岗位时，一张清单只用一个岗位的身份操作，不自动替他办下一环。
4. **点击回执。** 点下去先显示「正在提交」；业务事务成功了才显示「已通过 + 时间」并禁用按钮。刚处理的那行在本次视图里保留结果，下次打开默认只列未办；已办另有入口查回。**打开过详情不算处理过。**
5. **钱分开算。** 申请金额、批准金额、实际已付分开统计，不相加；只有部分金额已知时写明「其中 × 笔金额未知」。
6. **定时汇总。** 本次批次 = 截止前已进入本岗位阶段、现在仍待本人处理的全部单据；区分「本批新增」和「以前未办」。新增区间是（上次截止，本次截止]。没有待办不发空通知，但记下「今天查过了」。错过时刻恢复后补一次当天的，不补发多天。发送前再过滤一遍已办和已撤权的。
7. **批量（后置）。** 选中项先预览：逐项列金额、风险、版本、将执行的动作，不默认全选。确认时逐项重新核权限和版本，变了的跳过并说原因，结果逐笔返回。结果不明先按原请求号回查，不整批重放。付款岗位不做「一键全付」。

## 5. 验收（并进设计稿第 5 段，挑至少三条）

| 场景 | 必须看到的结果 |
|:--|:--|
| 三个岗位各有多笔待办 | 每人只看到本人权限内的；手机上能展开原件、处理、回到列表；空清单有说明 |
| 店长点了「通过」 | 那一行变成「已通过 + 时间」，其余行的按钮不错位；老板的清单里出现这一笔 |
| 老板通过之后 | 出纳清单里出现「待付款」；页面上「已批准」和「已付」分开显示 |
| 用旧卡片、越权身份、重复点击 | 都被拒绝或只生效一次，回执说清原因 |
| 定时汇总当天没有待办；汇总之后又来了一笔 | 不发空通知；新来的那笔手动打开清单能看到，第二天的汇总带上它 |
| 批量处理时其中一笔已被别人改过 | 那一笔跳过并说明原因，其余逐笔回执 |
| 某家店的数据暂时取不到 | 清单写明这家店暂未取得，不显示「全部已处理」 |

## 6. 不变量（并进设计稿第 6 段）

- 权限只认服务端的身份和授权，卡片上显示的岗位名不是依据。
- 清单是查询结果，不是第二份审批记录。
- 批准和付款是两件事；页面上永远分开显示。
- 跨店岗位的待办只走本人私聊，不在门店群里广播。
- AI 建议只是参考（例：建议通过 / 不确定 / 着重审查）；证据不足就是「不确定」，不默认给绿灯。建议不决定权限，也不决定放不放行。

## 常见走偏

- 统一清单形态时，把出纳的「办理付款」改名成「通过」。改名不改含义。
- 老提醒系统没关，新私聊清单又发一遍，同一笔被提醒两次。上线时把旧的群内催办、逐单通知一起列清楚。
- 用「刚处理的那行消失」当成功反馈，后面的按钮跟着错位。
- 按最初报账时间算「今天的单」，漏掉昨天报、今天才流到本岗位的。
