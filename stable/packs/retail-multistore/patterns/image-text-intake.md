# 模式 · 图文办理（v0.1.0）

> 员工在群里或私聊里，用几句话加几张图报一件事。系统要做到三件事：**接得住**（每条都有回音、原件不丢）、**看得懂**（先 OCR，不够再看原图，几条消息归成一件）、**只问缺项**（齐了就往下转，不让人反复确认）。
> 适用：报销、进货单、维修申请这类「一件事 = 文字 + 图片 + 金额」的办理。不适用：纯表单录入（没有聊天入口）、需要实时对话的客服。

## 1. 目标（并进设计稿第 1 段）

写清这三件事各做到什么程度算完，并引用使用者原话：

- 接得住：员工发出的每条消息都有回音；图片先存好再解释；系统重启不丢件。
- 看得懂：同一个人连着发的几条归成一件；一句话里的两件事拆成两件；两个人交错发不串。
- 只问缺项：资料齐了就转给下一位办理人；缺什么只问什么，一次只问一个必要问题。

## 2. 口径（并进设计稿第 2 段，全部〔待裁〕）

| 〔待裁〕 | 为什么要使用者定 | 常见候选（只是帮你想全） |
|:--|:--|:--|
| 转给下一位之前，哪几项必须齐 | 这是「什么算报完了」，是业务判断 | 金额、事由、费用大类、真实发生日期 |
| 图片是硬门槛，还是建议上传 | 有的老板要凭证，有的老板先信人后补 | 硬门槛 / 建议但不拦 / 按大类分别定 |
| 资料齐了以后，直接转，还是让员工再确认一次 | 多一次确认就多一次打扰 | 直接转 / 摘要确认一次 |
| 大类从哪来 | 员工原话、已确认的对应关系，还是让 AI 猜 | 只认原话和已确认的对应；模糊就问 |
| 已经垫付和待付款的账单怎么分 | 关系到后面谁付钱给谁 | 垫付报销 / 待付款账单 / 不确定就问 |
| 哪些场景要 AI 内容核验 | 核验花钱也花时间 | 全部核验 / 只存不验、由店长看 / 按大类定 |

〔待裁〕没定之前，实现照常推进：做成可配置，配置旁边写「待裁」，正式启用清单列出未定项。

## 3. 数据源与对象（并进设计稿第 3 段）

先复用仓里已有的收件、队列、存储模块，不另起一套。需要新增时，最少要有这几种对象：

| 对象 | 最少记什么 | 为什么单独存 |
|:--|:--|:--|
| 收件记录 | 收件编号、平台消息编号、群和人、接收时间、原文或资源标识、状态 | 先给编号和回音；按平台消息编号去重 |
| 原件 | 原件编号、所属收件、哈希、受控存放位置、保存状态 | 原件和识别结果分开；识别失败不丢图 |
| 识别片段 | 原件编号、识别方式（OCR 或看图）、识别器版本、页码或区域、内容 | 能说清每个字段是从哪来的 |
| 归集批次 | 人、事项线索、成员收件、批次代数、到期时间、状态 | 时间窗只帮着归集，**不等于一笔费用** |
| 单据版本 | 单据编号、版本号、材料版本、事实字段、唯一事实摘要及其哈希 | 已审核的版本锁定，后补的材料进新版本 |
| 纠错记录 | 原单和版本、反馈人和原话、员工报告的问题、核查后的归因、修订前后差异、确认人和时间 | 用于事后分析；不和执行失败日志混用 |

金额用整数分存；金额可以为空，空和 0 分开。

## 4. 分步（并进设计稿第 4 段）

按顺序做，每一批能单独交付，不等全部做完才上线。

**第一批：接得住**

1. 平台回调里只做三件事：写收件记录、写待办任务、写回执意图，然后马上应答平台。识别、模型调用一律不放在回调里。
2. 回执分级说，不编百分比：「已收到」→「还缺 ×× 」→「已补齐，已交 ×× 处理」→「已保存，但转交暂未完成」。数据库没写成功，不许说已收到。
3. 下载原件走单独的队列，和识别队列分开。下载成功才说「原图已保存」；下载失败说清楚是哪一步失败、能不能重试。
4. 分别记三个耗时：存好、应答平台、员工看到回执。三个目标值是工程默认，上线前用真实环境实测定，不报本机模拟的速度。

**第二批：看得懂**

5. 先 OCR。开工前先盘点仓里有没有能用的 OCR，没有就先做接口和隔离验证，不上线一个总是失败的空壳。
6. OCR 不够、字段互相矛盾、手写、版式复杂时，再让多模态模型看原图。触发条件要能解释、能配置。合计由程序算，不让模型算。
7. 同一个人连续发的消息，用一个可配置的静默窗归集：新消息到了就顺延，员工说「发完了」可以提前结束。截止时间存进库，靠队列扫描恢复，不只靠内存里的计时器。识别结果晚到，回到原批次，不另开一件。
8. 回复了哪条消息，优先按回复关系归；时间接近只当候选。同额、时间接近都不能当成同一笔的证据。

**第三批：只问缺项**

9. 照第 2 段定下的必填项判断齐没齐。缺什么只问什么；来源互相矛盾时只问矛盾的那一项。
10. 齐了就转。如果第 2 段定的是「直接转」，事件记成「系统转交」，带上原提交人、来源消息、单据版本和触发原因。**不生成「员工已确认」这种事件。**
11. 同一个版本只生成一份事实摘要（事由、大类、金额，加上已知的门店和日期），由已存的事实按规则拼出来。员工看到的回执和审批人列表里看到的概述，用的是同一份，不让模型写两遍。
12. 纠错走单独一条路：员工指出摘要不对 → 先存原话，回「已记下，正在处理」→ 暂停这个版本的审批按钮 → 对着原材料找差异，没依据就追问，不猜新金额 → 出一版修订，只在这里让员工确认 → 确认后成为新版本，重新进入审批。已经批准或已经付款的单，保留原来的决定和付款事实，按更正流程走，不倒回待审批。

## 5. 验收（并进设计稿第 5 段，挑至少三条）

| 场景 | 必须看到的结果 |
|:--|:--|
| 员工先发「打车费」，再发「28」，再发一张图 | 每条都及时有回音；原件能查到；三条归成一件；服务类费用不硬配商品 |
| 两个人同时发；同一个人连着报两笔 | 不同的人不串；同一个人的两笔分开；没有凭同额或时间接近合并 |
| 一张清楚的票据；一张模糊或手写的票据 | 前一张走 OCR；后一张触发看原图；能看到每个字段走的是哪条路；仍看不清就只问必要字段 |
| 下载失败；服务重启；识别结果晚到 | 已收的件不丢；下载失败不说已保存；任务能接着跑；晚到的结果不覆盖新材料 |
| 资料一次齐全 | 直接进下一位的待办，回执说清交给了谁；不多问一次确认（如果第 2 段定的是直接转） |
| 员工说「金额不对」 | 原版本审批按钮失效；修订版员工确认后才重送；纠错记录里同时有「员工报告的问题」和「核查后的归因」 |

再加一条反向用例：注入一张故意缺金额的单，它必须停在「还缺金额」，不能被转走。

## 6. 不变量（并进设计稿第 6 段）

- 原始消息和图片永远保留；OCR 和模型意见是派生记录。
- 收件编号、单据编号、分类编号是三种编号，不混用。
- 已审核的版本锁定；后补的材料进新版本，旧的批准不自动沿用到新金额上。
- 没有回复不等于确认。系统转交、员工确认、员工报错是三种事件，各记各的。
- 错误反馈不直接改全局规则、词库或权限。
- 纠错记录里，没查清的不写成「程序出错」，更不写成员工的错。

## 常见走偏

- 把「收到图片消息」说成「原图已保存」。下载还没完成。
- 为了少问一次，让模型补出金额或收款方，再当成员工说的。
- 用一个「处理中」盖住收件、识别、转交三个状态，员工不知道卡在哪。
- 把员工阶段的确认步骤删掉时，顺手把必填项检查也删了。两件事分开改。
