# 设计在用与否 · 七态判据（v0.1.0）

> 性质：判据件。回答「某个设计 / 机制 / 目录 / 探针，是真的在用，还是只是登记过、在跑没人看、睡着了」。第二个环转没转，先要能判出哪个零件真在转。
> 出处：判据是 AI 在一次三层盘点里定的——**第④类出处（AI 现编），用户可改**；四类证据的权重与「≥2 类」这条线用户没拍过。正本见套装 README 的对应表。

## 1 四类证据（窗口：近 30 天）

| # | 证据 | 例 |
|---|---|---|
| ① | 机器读写 | 定时跑了 / hook 命中 / 被脚本 import |
| ② | 会话调用 | Skill 被调 / 路由命中 / 文件被读 |
| ③ | 产物在长 | 目录内文件新增、修改（扫场改动不算） |
| ④ | git 提交 | 非扫场提交 |

**扫场不算证据**：批量补登资产卡、全仓行尾规范化、建仓一次性入库、批量放行 `.gitignore`、一次提交碰很多顶层目录（阈值自定，例：≥12 个）；以及登记类文件（资产卡、项目状态件、自动重生成的清单）的改动。

## 2 七态

| 判 | 定义 | 证据 |
|---|---|---|
| **在用** | 近 30 天有 ≥2 类独立证据 | 四类证据任两类 |
| **结构性在用** | 不产文件，但新东西按它落位 | 近 30 天的归位事件（例：按目录分组规范新建了一格） |
| **在跑但没人看** | 机器在跑、产物在长，零消费 | 有定时或服务，无读取 / 引用痕迹 |
| **登记过没在用** | 只有资产卡 / 状态件 / README 指针类的扫场改动 | 只命中扫场批次 |
| **休眠** | 有过使用证据（> 30 天前），近 30 天无 | 90 天窗口内有、30 天内无 |
| **概念 / 空房** | 规范里有名字，没有实物，或实物从未被读写 | 被规范件引用 ≥1 次，四类证据全零 |
| **按设计不动** | 归档类、已发布的完成态作品：静止是对的 | 不判 |

## 3 分得清的四对

1. **设计在用 vs 设计的说明书没在用**：目录分组本身在用（新东西按它落位），描述它的 README / 索引没人读。
2. **在用 vs 登记过**：一个有两条定时、上百个文件在长的派活内核 vs 一个只有一张补登资产卡的目录。登记机制本身在用，不代表它登的每张卡对应的东西在用。
3. **在用 vs 在跑没人看**：夜里跑、产物被开场注入每场读到 vs 每天定时跑、花钱、没有谁读的痕迹的简报。没有到场口的探针也是这一族。
4. **规范指着的房子 vs 房子里有人**：被规范引用多次、零活动的目录；零调用的 skill；刚建好、还没等到第一次触发的路由（这种给时间，不急着判）。

## 4 和第二个环的关系

- 探针是第二个环的读数口；探针本身也要过这张表：**「在跑但没人看」的探针 = 环没转**。治法是给它一个到场口（开场注入一行、收件箱一条），不是再加一个探针。
- 「登记过没在用」是资产线最常见的假象：登记 ≠ 被用；资产线的验收看「被真实需求方使用」。
- 「概念 / 空房」回答「规范里写了的东西有没有实物」——复盘时当框架缺口回填（A 模板第 7 节）。
- 这张表判的是「在不在用」，**不判生死**：归档、删除、合并走 report-only 菜单 + 人拍板。

## 5 机器化到哪一步

- **休眠已机器化**（运行件见 `probes-howto.md` §6）：顶层目录休眠满 60 天，自动把它在索引文件里的表格行摘到文件末尾「休眠」段、给资产卡写 `dormant_since`；再活跃自动挪回。判据：git 与文件系统两边最后一次**非扫场**活动都早于 60 天；「按设计不动」走白名单；一点证据都没有的目录不判（宁可漏摘，不瞎摘）；只动表格数据行，散文行不动（一行常写好几件事，整行挪走会误伤活的那件）；写卡后还原 mtime，不污染自己要测的信号。
- **七态已由观察器机器判，外加第八态 `unspecced`**（运行件 = toys 的 `dispatch-kernel/observers/in_use_scan.py`，2026-09-24；它不重写上面的休眠判据，而是把休眠脚本的只读读数当一个来源组合进来）。五类对象：toys 顶层目录、项目级 skill、hook 路由、指向项目树的计划任务、派活维度；登记面（资产卡、资产总表）与规范件引用只当旁证。
  - **第八态 `unspecced` = 无规范 → 不可调用**：被扫的东西缺目录规范、缺内容规范，或者某类证据没有声明输出口时，不写特判绕过，判 `unspecced` 并写清缺的是哪一样。它是读数不是失败——回头给那个件补规范或补输出口，下次扫描自动升级。
  - **在用只按量到的正证据数类**（≥2 类）；只量到 1 类、差的那一类恰好没有输出口 → `unspecced`。零侧四态（休眠 / 登记过没在用 / 空房 / 在跑但没人看）照判，但「会话读文件」只量得到路由注入这一路，零是下界。
  - 逐类对象的落法：目录 = 休眠脚本的窗口切线（它吐活跃目录条目时 ③④ 分开算，老版不吐时合并成一类）+ 计划任务 / 派活维度（①）+ 路由注入 / 会话里跑它的脚本（②）；容器目录按「新成员按它落位」判结构性在用；skill = Skill 工具调用次数（来自会话普查脚本的机读输出），≥2 场独立会话算在用、只 1 场 → `unspecced`；路由 = 路由台账命中，≥2 场独立会话算在用、只 1 场 → `unspecced`、glob 路由不进台账 → `unspecced`；计划任务 = 窗口内跑过或在跑（①）+ 有没有规范件引用 / 路由注入（有人看）；维度 = 窗口内 ≥2 天真跑。
  - **疑坏**是告警标记不是第九态：计划任务最近一次结果非零（扣掉「正在运行」两种良性码），或维度启用着却窗口内一次真跑都没有。
- 2026-09-24 首次真跑（30 天窗口，本机约 4.7 s）：在用 24 · 结构性在用 2 · 在跑但没人看 6 · 登记过没在用 23 · 休眠 12 · 概念·空房 2 · 按设计不动 14 · `unspecced` 50；`unspecced` 里 45 个来自三个输出口缺口（活跃目录的 ③④ 分不开、skill 调用计数、逐条路由的消费读数），这正是下一步该补规范的清单。
- 补了两个输出口之后（同日；休眠脚本吐活跃目录条目、会话普查脚本加机读输出）：在用 50 · 结构性在用 2 · 在跑但没人看 6 · 登记过没在用 19 · 休眠 16 · 概念·空房 6 · 按设计不动 14 · `unspecced` 20——剩下的全是输出口缺口（会话里直接读文件、不经 Skill 工具的读取、逐条路由的消费、glob 命中）。两个口解锁了 30 个对象：补规范先补声明输出，目录与内容规范其次。
- 还是人判的：「结构性在用」只判得到容器目录（新成员按它落位）；更高一层的分组设计（例：整个项目树的顶层分组）仍靠人读归位事件。

## 6 怎么跑 / 怎么读 / 别的项目要同样的读数

**怎么跑**（在 toys 里；路径相对 toys 仓根，`<toys>` = 工作台仓，私有、本机）：

```
python dispatch-kernel/observers/in_use_scan.py                  # 观测：stdout 一个 JSON 数组（work items），写 state
python dispatch-kernel/observers/in_use_scan.py --full           # 全量 JSON：sources / objects / pairs / unspecced / alerts / items
python dispatch-kernel/observers/in_use_scan.py --md             # 写 dispatch-kernel/reports/in-use-<日期>.md（不写 state）
python dispatch-kernel/observers/in_use_scan.py --full --days 14 # 换窗口（默认 30，含今天）；换窗口那次不做变化比对
python dispatch-kernel/test_in_use_scan.py                       # 自测：合成数据、子进程打桩，不碰真实文件
```

零模型额度，只读；状态 `dispatch-kernel/state/in-use.json`（上次全量的逐对象判定），只在无参观测或 `--full` 时写。人不用敲这些——它按派活内核的观察器规范写（无参可跑、stdout 一份 JSON、空数组 = 期望态满足），接进维度或夜间杂务之后由定时代提问。

**怎么读**：

1. **先看 `sources`**：每个来源 `ok / error / spec`。单个来源坏了只标它自己，其余照扫；依赖它的对象判定为 `null`（未判），不当零，也不参与变化比对。
2. **再看 items（无参输出）**：只有两种东西会进来——处在三种要人到阀上的状态之一（在跑但没人看 / 规范指着的空房 / 疑坏），或判定自上次扫描变了（带 `prev_verdict`）。空数组 = 没事。
3. **`unspecced` 按「缺什么」读**：`unspecced_by_reason` 把对象按缺口归堆，一个缺口一行——一行就是一张补规范的工单（缺输出口 → 给那个件加机读输出；缺目录 / 内容规范 → 给那个件补规范）。
4. **`pairs` 是四对的计数**：设计在用 vs 说明书没跟上、在用 vs 登记过、在用 vs 在跑没人看、规范指着的房子 vs 房子里有人。
5. **判定带出处**：每个对象有 `evidence`（各类证据的计数或日期）、`classes`（窗口内量到哪几类）、`why`（一句话）、`missing`（`unspecced` 时缺哪样）、`caveats`（零是下界之类）。

**别的项目要同样的读数（松耦合）**：

1. **先查询，不复制**：观察器只在声明的输出层组合——子进程 + stdout JSON、已有的状态文件、有规范的文件格式；不 import 任何被组合件的内部函数。别的项目要读数，读它的 `--full` 输出或状态文件就行，不要把代码拷走。
2. **照结构长，就量得到**：一级目录 + 索引表格行 + 资产卡（休眠脚本 `--root` 能指过去）；路由配置 + 路由台账（每行 `ts / sid / matched / files`）；派活维度 yaml（五格）+ 运行记录目录（`<日期>-<时分秒>-<维度>`）。长成这样的项目，同一套判法直接适用。
3. **没有规范的件就是 `unspecced`**：别为它写特判；给它补目录规范、内容规范或输出口，读数自己会升级。常见的三个输出口缺口：会话里直接读文件（不经 Skill 工具）没有机读输出、逐条路由的消费没有机读输出、glob 命中不进路由台账。
4. **没有这套运行件的项目**：复盘时 A 模板第 6 节照实写「无读数（没有运行件）」，不写 0。

## 7 负空间

- Skill 调用只数得到经 Skill 工具的调用；别的宿主的使用、直接读 SKILL.md 的都数不到——**都是低估**。
- 「产物在长」用文件修改时间：数据目录会把读数撑大，撑大的是数据量，不是使用密度。
- 记忆与判断层的「在用」只证得到写；召回要靠记忆召回对账那块探针。
- 30 天窗口对季度节奏的东西（述职、考试冲刺材料）不公平。
- 计划任务的非零退出码不一定是故障（有的程序正常退出码就是 1），要逐个查，查之前标「疑似」。
- 观察器的 `unspecced` 大多来自输出口缺口，**不等于没在用**：手工盘点能直接读 git 与会话文件，观察器按规矩只读声明输出，所以两边的数不会一样；差在哪要看 `missing`，别拿两份读数直接相减。
