# CG 维护操作

本轮把令牌权限、反馈回流、验证和备份变为可执行能力。CG 仍提供材料与协作记录，harness 各自负责真实执行。

## 验证与发布

仓库根目录运行：

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
pnpm install --frozen-lockfile
pnpm verify
```

验证环境使用 Python 3.12、Node.js 24 与 pnpm 10.17.1。`requirements-dev.txt` 固定 PyYAML 版本，供安装器回归读写完整 YAML 记录；它不是网页或工作台服务的运行时依赖。

统一入口依次构建、检查在线发布包、执行 Node 与 Python 回归、验证检查器自身测试以及三页规范，任一步失败退出非零并停止后续步骤。`dist/verification.json` 留下源码提交、时间、命令与结果；未提交的本地改动仍需结合 Git diff 审阅，提交号不能代替工作区检查。

`.github/workflows/verify.yml` 在 PR、main 更新和手动触发时运行同一入口。检查通过后才构建容器、上传可部署产物。失败仍上传验证报告。工作流不自动部署网站；仓库分支保护是否要求该检查，由 GitHub 设置决定，不能仅凭存在 workflow 就声称无法绕过合并。

`release-lock.json` 固定两份在线包的版本和 ZIP 摘要。`scripts/check-release.py` 同时核对安装源、该包的知识索引路径和摘要。修改包或随包分发的安装器后，先调整受影响安装清单版本，再更新锁：

```sh
python scripts/check-release.py --base origin/main --write
CG_VERIFY_BASE=origin/main pnpm verify
```

CI 对比 PR 基线或 main 前一提交，同版本内容改变会失败，即使有人重写当前锁。首次引入锁只能验证当前源与锁一致。此检查针对在线发布白名单，不等于全仓资产审计或每种宿主已实际兼容。

## 令牌管理

在“多 harness 接入”创建令牌，按项目及接入分发。新页面默认只读，按需增加提交、证据和撤回，设置到期时间。列表显示状态、范围、到期与最近访问，可调整或撤销。旧令牌不会自动缩小权限；升级后按实际用途逐个核对。权限与数据边界见 [接入契约](harness-api.md)。

## 从反馈到仓库回流

1. 项目用原客户端交反馈，获得原编号。
2. 维护者在反馈详情填写六项可公开摘要，检查不含凭证或私有业务数据，再生成下载。原始项目名、反馈文本、自查与历史不会自动复制。
3. 在 CG 仓库执行 `python scripts/import-backflow.py 下载文件.json`。默认生成 `.knowledge/downstream/pending/workbench/T-编号/`；不会覆盖已存在编号，不会操作 Git。
4. 在生成的 content/tests 中补实现或引用及真实验证记录，按原回流规范审核。摘要说“通过”不代表已经验证。
5. 只提交审阅过的目录，例如 `git add -f .knowledge/downstream/pending/workbench/T-实际编号`，再创建 PR。回反馈页填写 PR 地址，原记录保留关联历史。
6. 合并后按实际交付更新版本、索引、发布锁和处理状态；发布前运行统一验证。不能把“关联 PR”直接当作已合并或已有成品包。

候选目录下的 source.json 保存来源编号与摘要；传统 backflow.yaml 的历史登记仍需人工核对，未自动改写旧条目的结论。

## 备份与恢复

使用 [独立部署说明](self-hosting.md) 中的在线备份和恢复命令。工具拒绝覆盖目标，核对摘要、SQLite 完整性和迁移记录；恢复到新目录后再切换。Compose 只开放回环端口，公网入口由自己的 HTTPS 代理提供。
