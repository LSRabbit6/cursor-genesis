02 / 两端职责

同一个回路，各自负责哪一半

服务端视角

CG 供给与维护侧
生产与组合
将可复用方法整理为原子组件，再组合为使用者能选择的场景包。
交付什么
规范、步骤、模板、检查器、适配说明和可识别的版本。
接收什么
实际使用过的问题、改进、来源版本与验证证据。
谁决定
维护者决定是否通用化、放在哪里、如何发布；具体业务口径留在项目。

客户端视角

使用者的 AI＋项目
理解与判断

如何验收

留下什么

03 / 交接内容

六个环节，把两端一项项对齐

每个环节都保留“谁做什么”和“交给对方什么”。展开可以看到细节；手机上两端会按顺序上下排列。

① 了解与选择 · 先判断是否适合当前项目

服务端提供

包说明、领域清单、适用条件与能力边界。缺少成品的领域明确说明已有的是模式或骨架。

客户端完成

读取本仓与使用者原话，确认已有系统、使用者、对象与材料，再选择合适的包。

交接：包名、能力说明、所需材料。没有根据的事实写“给不出”；未确认业务口径交给负责人。

本仓的 domain-menu 是静态领域清单。在线菜单版另见下方单独说明。

② 获取与安装 · 文件到场，版本有记录

服务端提供

已发布材料、安装清单与版本；以对应包的 README 为取用入口。

客户端完成

获取选定版本，使用本地安装器或该包说明的方式落仓，核对安装改动与记录。

交接：包内容与清单 → 项目文件与 installed-packs.yaml。目录存在不等于所有包都支持同一种安装方式。

源码依据：安装器 · 数据应用包清单

③ 接入与加载 · 分清“装了”和“用上了”

服务端提供

规则指针、技能入口、检查器命令和已有宿主适配样例。

客户端完成

核实宿主实际读取的位置、技能能否调用、检查能否运行；自动触发单独验证。

交接：通用材料 → 具体宿主中的读取、调用与触发入口。需要记录实际生效的证据。

已安装→已接入→已加载→已触发→检查通过

当前数据应用包只随附 Claude Code 的自动触发配置样例。其他宿主须核实自己的接入方式；手动检查通过只证明这次手动执行。

④ 实施与验收 · 在项目中把事情做完

服务端的作用

提供已经下载的工具与方法来源。已装材料可以本地运行，CG 无需逐次参与项目检查。

客户端完成

先写设计稿，再实施、运行检查与回归、查看交互结果，达到约定后按授权交付。

交接：产物、可重跑的验证证据、已知限制与待拍板问题 → 使用者。

机器检查覆盖的是明确契约；它不能证明全部体验与业务含义。源码已提交、已合并、已正式部署，也分别需要证据。

⑤ 问题与改进回流 · 找对接收方

服务端完成

维护者判断改进的真实性与可复用性，决定接受、补充、调整或暂不做。

客户端完成

真实代码缺陷修实现；工具问题按包约定反馈；业务口径待裁项留给业务负责人。

交接：问题现象、发生位置、来源版本、改进内容和验证材料 → Issue / 回流 PR。

已提交不等于已接受，已接受不等于已发布。不应修改检查器或忽略失败来制造“通过”。查看回流规范

⑥ 发布与再次采用 · 让改进真正回到使用中

服务端完成

把接受的改进提炼为通用材料，验证后发布，并说明适用范围与变化。

客户端完成

查看版本与说明，评估是否采用，更新后重新验证实际加载、触发和效果。

交接：新版本与变化说明 → 客户端采用记录 → 新一轮使用证据。

流程中存在“更新”一步，不代表所有客户端会自动升级，也不代表已经建立定时跟进。

04 / 下游观察到的扩展路径

在线菜单：同一分工，换一种交接入口

历史观察：旧部署源码未在此核对。 下游环境用过在线 domain-menu v0.2；本仓现已增加独立的协作工作台。下面保留旧部署的观察说明；两者不共享票据、令牌或私有数据。
拿清单→本仓自查→交回→按回执做→过几天查编号

服务端视角

该观察版本按类型查表：有包返回材料和设定，缺口登记并给出编号及已有骨架。维护侧再判断是否补成通用组件。

客户端视角

AI 在本仓回答清单与选择类型，提交选定内容和已装版本；按回执接入工具，随后按编号查询。

查看每次请求、回执与离线处理
清单与版本
客户端发读取请求；服务返回问题、类型表、模板和包目录。
提交答案
发送类型、答案、选定材料、项目名及已装包版本；返回总回执和各类型结果。
安装
按包名取材料；客户端校验、安装、记录版本并接入宿主。
反馈
发送类别、位置、现象和版本；返回登记编号，不表示已修复。
查进度
按编号取状态、说明和关联包；有包后再评估安装。
连通失败
已观察客户端会暂存提交 / 反馈，恢复连接后补交；已装材料可继续本地用。任务明确要求起步失败停止时，先遵守该任务约定。
传输范围
填写到答案中的内容会发出；客户端不自动上传整个仓库。凭据不进入答案与公开材料。
