# CG 协作工作台 · 设计稿（2026-09-26）

> 身份与部署方向已按用户要求修订，现行设计见 [CG 独立身份与多 harness 接入](2026-09-26-cg独立身份与多harness接入.md)。下文保留首版设计背景。

## 1. 目标

使用者原话：先“一个整体架构图”，下面分别是“服务端视角”和“客户端视角”；在确认完整协作流程、真实操作看板、网页上线三个范围后，要求“全部 设计的开干吧”。在保留架构说明的基础上，提供能实际提交、登记、处理、查询和取包的入口。

## 2. 口径

CG 按类型查表，不代替项目推演。数据应用有包；企业按现有材料说明；零售、病理只给模式和待补编号；其他给通用骨架。是否接受、如何处理由维护者操作并记录原因。未发布的包不能标成可安装。安装、加载、检查、验收分别记证据，不推断自动完成。不同使用者的记录隔离；同一使用者可切换两个视角，项目令牌只能访问被授权的项目。

## 3. 数据源

只读本仓发布材料、安装清单、架构说明，构建带摘要的下载包。服务写入持久数据库的白名单是需求、回执、票据、状态历史、项目令牌摘要和客户端执行证据；不访问任何业务后台。线上用平台数据库与登录身份，本地用 SQLite 和仅回环地址的入口。页面不会自动扫描或上传仓库；客户端仅上传明确填写的答案、反馈和已安装包版本。

## 4. 分步

1. 建立可共享的服务逻辑、本地运行入口、数据库迁移和包目录构建。
2. 实现清单、提交、幂等回执、票据查询、反馈、维护处理、执行证据和项目令牌。
3. 实现 Python 标准库客户端，包含离线暂存重交和安全下载安装。
4. 将整体图和双视角工作台接上同一批真实记录，提供搜索、状态筛选、详情与历史。
5. 运行接口、权限、幂等、持久化、安装和回归检查，记录已知限制。
6. 提交仓库，发布仅本人可访问的网页并核实部署结果。

## 5. 验收

- R1 / R3：中文元信息与零外部页面依赖：`python3 stable/packs/delivery-data-app/validators/data-app-norms-check/scripts/check_data_app_norms.py web/index.html`。
- S2 / S3 / S4：票据有检索、空态解释、提交和处理有回执；接口验收：`node --test service/tests/*.test.mjs`。
- 两端共享持久记录，跨身份与跨项目访问被拒绝，重复提交不新增编号，状态更新冲突被识别：同上测试。
- 客户端下载校验、越界拒绝、离线重交：`python3 -m unittest discover -s scripts/tests -p test_menu_client.py -q`。
- 原回归：`python3 -m unittest discover -s scripts/tests -q`；既有 Mac 路径检查缺陷若影响新下载链路，修实现并保留原测试判据。
- 可构建发布：`npm run build`；实际部署必须成功才报告线上可用。

## 6. 不变量

- 页面零 CDN、外部字体、外部图片依赖；已有离线架构页保留。动态操作需要服务，断线明确提示并保留输入。
- 不接管项目运行，不改变现有业务后台或业务判据，不上传真实客户资料。
- 业务口径留给使用者；不自动审批、发布包、升级项目或宣称宿主自动触发生效。
- 令牌仅保存摘要；项目令牌不能维护票据或访问其他项目。生产数据与凭据不进 Git。
- 原子组件与场景包由本仓发布源构建；不能凭空制造可安装包或把状态变更冒充真实发布。
